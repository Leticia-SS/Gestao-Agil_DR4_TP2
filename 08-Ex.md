# Exercício 8: Classes de serviço no backlog do RotaViva

## Classificação de seis itens hipotéticos

1. Correção de falha de segurança que expõe dados de rotas de clientes: classe Expedite.
2. Bug que impede o cálculo de rota para um cliente estratégico: classe Expedite.
3. Correção de erro de cálculo de custo que afeta vários clientes mas tem contorno manual: classe com prazo fixo, ou seja, data comprometida.
4. Ajuste no algoritmo de roteirização para reduzir combustível dos clientes maiores: classe padrão.
5. Melhoria de usabilidade na tela de cadastro de pontos de entrega: classe padrão.
6. Troca de biblioteca interna de logs, sem impacto visível ao cliente: classe preenchimento, ou seja, trabalho de menor prioridade que ocupa capacidade ociosa.

## Critério usado para atribuir cada classe

O critério evita classificar tudo como urgente porque exige uma justificativa objetiva para cada classe. Expedite fica reservado para itens que param a operação do cliente ou expõem risco grave, e tem limite de quantidade em andamento. Prazo fixo é para itens com data externa comprometida, como contrato ou obrigação regulatória. Padrão é o fluxo normal, com prioridade pelo custo de atraso. Preenchimento é para itens que não têm urgência nem prazo e podem esperar capacidade livre. A regra é: se o item não tem consequência imediata mensurável para o cliente ou para o negócio, ele não é expedite.

## Sinalização visual no board

O board deve diferenciar as classes por cor e por raia. Uma raia superior ou lateral destacada em vermelho para expedite, com limite visível de um item em andamento. Uma marcação em amarelo para prazo fixo, com a data comprometida exibida no cartão. Cartões em branco ou azul para o fluxo padrão. Uma área separada ou etiqueta cinza para preenchimento. A cor e a posição no board tornam a classe visível para toda a squad e para os stakeholders, e o limite de expedite fica explícito no próprio board, não só na política escrita.
